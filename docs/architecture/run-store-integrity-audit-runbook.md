# Run Store integrity audit — activation and incident runbook

**Owners:** [#1690](https://github.com/BestNathan/nession/issues/1690) and [#1742](https://github.com/BestNathan/nession/issues/1742). This procedure covers the optional **read-only** `CI / Run Store Integrity Audit`; it does not authorize a writer or attest historical content.

## Before activation (do not skip)

1. Confirm that **main** remains the trusted workflow source. Review production GitHub Rulesets for each of `acceptance-results`, `task-results` and `metrics`. Record whether ordinary fast-forward edits, force-push, deletion and unauthorized writer identities are actually blocked. If they are not, document the limitation under #1690; a successful audit is **not** a substitute for server-side authorization.
2. From an independently controlled, read-only backup, identify and manually review each orphan ref's **migration baseline** commit and manifest. Capture the baseline outside all three orphan branches. This does **not** retroactively authenticate data preceding those commits.
3. Under separately administered secret access, provision `RUN_STORE_AUDIT_ANCHORS_JSON` as an exact JSON object with three 40-hex SHA-1 commit IDs: `acceptance-results`, `task-results` and `metrics`. These values must come from the independently reviewed baseline, **never** from live ref tips or a `workflow_dispatch` input. Keep an independent signed/WORM checkpoint under a different authority when available. A repository secret alone is **not WORM**, and GitHub admins may change it.
4. Only once the anchors are verified, set repository variable `RUN_STORE_AUDIT_ENABLED=true`. For a **safe manual trigger**, use the authenticated default-branch `repository_dispatch` event `nession-run-store-integrity-audit` via `gh api -X POST repos/BestNathan/nession/dispatches -f event_type=nession-run-store-integrity-audit`, then review its run ID, attempt, exact main SHA and failure/success evidence. **Never use `workflow_dispatch` for this secret-bearing workflow:** it can execute a modified workflow from an arbitrary branch and leak the anchor secret. Scheduled executions use the same default-branch read boundary. Do not enable with unverified anchors merely to obtain a green check.

## What a green or red run means

A successful `./gates/run run-store-integrity` is **offline fixture evidence only**. A real successful job proves that the fetched branch tips matched the GitHub REST API tips at observation time and that all Git history *after the supplied baseline* followed the path/ancestry classifier. It does **not** prove the writers were authorized, that a baseline is independently immutable, or that a deleted/ref-replaced store is safe. GitHub Actions logs are not an independent durable alert channel, and the workflow does not perform automatic repair.

On failure, **do not update the baseline, force-push, re-root, replay, or mark Success Criteria Pass**. Preserve the failed workflow URL/run ID/attempt/main SHA, separately observe the three ref tips and their parent chains, and snapshot the suspect Git objects to read-only backup. Compare them against the independent checkpoint. Identify the first invalid commit/delta and confirm its actual actor and writer provenance using repository audit logs. Escalate the alarm outside the repository; preserve source artifacts within their declared retention windows. Restore only after separately approved incident review using a new reviewed authorized writer/checkpoint, without hiding the incident by replacing old evidence.

## Rotation, recovery and rollout boundaries

Rehearse a **read-only restore drill** on an isolated clone before production activation. Rotate anchors and writer credentials only under independent review with documented old/new signed checkpoint, verified ancestry and no silent history rewrite. Observe real Acceptance Case/Scenario/Test, Task and Metrics ingestion after restrictions are rolled out. The separate `agent-store` ref was provisioned after the historical three-ref audit was designed. It must hold only sealed/encrypted private checkpoint payloads; the four-ref signed checkpoint below does not make plaintext safe.

**Pending under #1690:** server-enforced Ruleset/App writer isolation, real negative writer attempts, independently administered WORM/signed checkpoint, external durable alarm delivery and proven read-only recovery. Keep those SCs Pending until independently authenticated live evidence exists.

## Public Sigstore four-Store checkpoint — #1690 SC-08 (new opt-in architecture)

The repository is public, so GitHub Actions `actions/attest@v4` uses the **Sigstore Public Good** service: the signed in-toto predicate is witnessed in an independently operated, append-only public transparency log. This is different from a GitHub Actions repository secret: an administrator can change a future Workflow or issue a new (visibly later) attestation, but cannot silently edit an already witnessed signature or backdate its transparency timestamp. It is a cryptographic **checkpoint integrity witness**, not a GitHub Ruleset or authenticated writer-identity check. For reference, GitHub documents the public log at https://docs.github.com/en/actions/concepts/security/artifact-attestations.

The main-only `CI / Run Store Signed Checkpoint` (`.github/workflows/ci-run-store-anchor.yml`) uses a weekly schedule, a change-scoped main push and a default-branch-only `repository_dispatch` trigger `nession-run-store-anchor`. There is intentionally **no** `workflow_dispatch`: a branch-selected YAML file could otherwise obtain the OIDC signing identity. Its token has `contents: read`, `actions: read`, `attestations: write`, and `id-token: write`, never Store Contents write or the Store Writer App private key. Only default-branch reviewed code may request the short-lived signing certificate. The same job must run the shared `run-store-integrity` Gate before signing.

The canonical writer-independent observation is `scripts/run-store-sigstore-checkpoint.mjs`. It fetches exactly `acceptance-results`, `task-results`, `metrics`, and `agent-store` into isolated temporary Git, cross-checks **each** fetched head against GitHub's REST ref, and records the commit SHA, Git root tree SHA, SHA-256 of the complete canonical recursive tree listing and entry count. It hashes the ordered four-Store manifest. The signed custom predicate embeds the full checkpoint JSON (not only its digest) so the external witness remains useful even after the separate **90-day** GitHub Actions artifact expires. The first signed state is labeled `new_observation_only_not_retroactive_attestation`: it cannot certify pre-existing content or old writer identities.

Before treating a run as evidence, verify **all** of the following on the same main run/attempt:

1. The `actions/attest` output includes a real attestation URL and public Sigstore transparency-log witness. The signer must be `BestNathan/nession/.github/workflows/ci-run-store-anchor.yml`, the predicate type `https://github.com/BestNathan/nession/attestation/run-store-checkpoint/v1`, and the GitHub OIDC issuer/trusted root must pass `gh attestation verify --repo BestNathan/nession --signer-workflow ... --predicate-type ...`. A model or an unverified JSON object is not a signature.
2. The verifier requires an exact SHA-256 subject/predicate match and a nonempty **cryptographically verified log timestamp**. Record the attestation identifier, witness/log reference, main SHA, run ID/attempt and canonical manifest checksum in the Issue before labeling the external checkpoint provisioned.
3. Recreate a temporary, **read-only** Git object database; verify all four pinned historical HEADs are still ancestors of current refs, compare all old Git tree/content-listing commitments, and invoke the canonical `auditAnchoredRunStore` for any subsequent commits. Any missing ref, history replacement, unexpected deletion or path mutation fails closed. The report is retained as an Actions artifact but is **not** a separate permanent backup of bulk Git objects.
4. For an incident, independently retrieve the **original** logged predicate/witness, verify it and compare it to the current refs before accepting a newly signed checkpoint. Never silently choose the newest checkpoint (a compromised signer could bless tampered history by issuing a later signature). Preserve the first contradicting log/time and Git ancestor as incident evidence; do not force-push or auto-repair.

**Authority and retention limits:** Transparency-log integrity survives a repository administrator's attempt to alter or delete local checkpoint files, but the main Workflow code and GitHub OIDC identity are still a trust boundary. A compromised authorized main Workflow can mint **new** attestations, so first-good checkpoint selection and incident alert escalation require independent review. The signed manifest certifies the Store snapshots, not repository Ruleset enforcement, individual record provenance, writer authorization, or confidential content handling. The related legacy `CI / Run Store Integrity Audit` with `RUN_STORE_AUDIT_ANCHORS_JSON` remains independently gated and should not be enabled from a fabricated secret. This Sigstore path requires real post-merge signer/verification/restore evidence before SC-08 can be marked Pass; a PR-only Gate or selftest cannot supply that evidence.

## Original Rekor checkpoint read-only audit (2026-11-03 implementation)

The legacy `RUN_STORE_AUDIT_ANCHORS_JSON` / `RUN_STORE_AUDIT_ENABLED=true` mode above is a **separate optional administrator-secret mode** and remains disabled without that administrator control. The existing `CI / Run Store Integrity Audit` Workflow now has a second, independent `public-sigstore-audit` job that uses no administrator secret and no Store Writer App token. It is active for trusted-main source changes, a daily schedule and default-main `repository_dispatch` event `nession-run-store-integrity-audit`. Arbitrary-ref `workflow_dispatch` is still prohibited.

**Original independent baseline, never re-learned from live refs:** `scripts/run-store-sigstore-audit.mjs` pins subject SHA256 `d6579886c6150f34b373901b29ad2aecf9d624b91004e7f87675d6dc3062e690`, source main commit `ccd0858b6bc06cf5c22e0efc1a9f2100974a568f`, GitHub signer run `41613325000` attempt 1 and public <https://search.sigstore.dev?logIndex=3665505739> (attestation <https://github.com/BestNathan/nession/attestations/63042719>). This is the **first known-good independently witnessed observation**, NOT a retroactive seal on preceding writes. It cannot be silently replaced by using a freshly re-signed copy of a corrupted remote ref.

The new auditor retrieves the **original signed DSSE bundle by its pinned subject digest** through GitHub's public repository attestation API, reconstructs and checks the *original* checkpoint payload bytes and their SHA256, independently runs `gh attestation verify` against the public Sigstore trusted root and exact signer Workflow/predicate, and requires Rekor inclusion at the **original** log index. It then fetches only the current four orphan refs into a disposable Git object database, proves that each signed historical head/tree/listing remains intact, checks ancestry and invokes the canonical `auditAnchoredRunStore` for every subsequent commit. There is no `git push`, no ref recreation, no source-selected executable checkout and no automatic repair.

The same job executes blocking `run-store-inventory` and `run-store-integrity` Gates, including existing unexpected-writer, source identity and forged receipt negative fixtures, then writes a separately labeled **isolated** tamper matrix. It signs the successful audit report with **another** public Sigstore/Rekor attestation; both the audit and fixture reports are retained as GitHub Actions artifacts. A failed baseline, unavailable public Sigstore API, unexpected Git mutation, missing ref, invalid signature, wrong signer/run, or failed Gate produces an attributed **failed GitHub Actions run with `::error::`**, an explicit fail-closed report when possible, and the retained artifact. No failed audit is considered an SC Pass. Expected detection of seeded **disposable** violations is evidence of the validator only, not an alert claiming real tampering.

To verify an incident, start with the *old pinned Rekor log* and the exact GitHub Action run/attempt and report; do not accept a newer independently signed observation as evidence that the old contents were authorized. Independently verify whether the failure was API visibility, expired credentials, Git HEAD drift, tampered files, unexpected records or missing upstream provenance. Never mutate a production Store during investigation. The public Sigstore log supplies an external cryptographic witness, but **does not establish PAT/App-only Ruleset write authorization (SC-02/03), external paging delivery, or pre-anchor historic provenance**. SC-07/11 may be promoted only after the separately authenticated live audit, drill and appropriate alerts have actually run and the canonical Acceptance has evaluated the precise evidence.
