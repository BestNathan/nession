# Per-Attach Env File Tracking Design

**Date:** 2026-07-15  
**Status:** Approved  
**Author:** Claude (with user input)

## Overview

Currently, env file source scripts in `/tmp/` are named per-session (`nession-source-{session}-{env}`), which means when multiple clients attach to the same session and source different env files, detaching one client cleans up scripts that might still be needed by other attached clients.

This design introduces per-client tracking so that when client A detaches, only A's sourced env scripts are cleaned up, not client B's.

## Goals

- Multiple clients can attach to the same tmux session and source different env files
- When a client detaches, only that client's env scripts are cleaned up
- Other clients' env scripts remain active
- Backward compatible with existing clients/agents
- Reconnect-friendly: clients reuse the same identity across reconnections

## Non-Goals

- Per-attach-per-session granularity (overkill for current use case)
- Actually unsetting tmux session env vars on detach (vars stay in session until kill)
- Server-side tracking of which client sourced which envs (agent manages locally)

## Architecture

### Core Concept

- **client_id**: UUID generated by client, persisted locally, sent on every connection
- **attach_id**: equals client_id (no additional derivation)
- **Script naming**: `/tmp/nession-{source,unsource}-{client_id}-{session}-{env}`
- **Cleanup scope**: per-client on detach, per-session on kill

### Data Flow

```
1. Client connects → sends client_id (UUID)
2. Agent receives client_id → uses as attach_id
3. Client attaches to session X → sources env "staging.env"
   → writes /tmp/nession-source-{client_id}-X-staging
   → tmux send-keys injects env vars (session-shared)
4. Client detaches → cleans up /tmp/nession-source-{client_id}-*
   → tmux session env vars preserved (other clients may still use them)
5. Session killed → cleans up all /tmp/nession-*-X-* (all clients)
```

## Design Decisions

### 1. client_id Lifecycle

**Decision:** client_id is tied to the client, reused on reconnect.

**Rationale:** When a client reconnects, it should be able to access its previously sourced envs. Generating a new ID on each connection would break this continuity.

**Implementation:**
- Web UI: stored in localStorage (`nession_client_id`)
- CLI: stored in `~/.nession/cli/client_id` file
- If storage is cleared, a new client_id is generated (treated as new client)

### 2. attach_id Generation

**Decision:** Agent-side, derived from client_id (attach_id = client_id).

**Rationale:** Simplifies implementation—no additional mapping needed. Both agent and server can compute it independently if needed.

### 3. client_id Provision

**Decision:** Client provides client_id in protocol messages.

**Rationale:** Client owns its identity. Server and agent just receive and use it.

### 4. attach_id Granularity

**Decision:** Per-client, not per-client-per-session.

**Rationale:** Simpler model. One client = one attach_id, regardless of how many sessions it attaches to. Cleanup on disconnect removes all scripts for that client across all sessions.

## Protocol Changes

### New Field: client_id

**ClientAuth message:**
```rust
pub struct ClientAuth {
    pub token: String,
    pub client_id: Option<String>,  // NEW: optional for backward compatibility
    // ... other fields
}
```

**AuthResponse message:**
```rust
pub struct AuthResponse {
    pub success: bool,
    pub client_id: Option<String>,  // NEW: agent assigns if not provided
    // ... other fields
}
```

**Backward compatibility:**
- Old client → new agent: agent generates client_id, returns in response, old client ignores it
- New client → old agent: agent ignores client_id field, uses session-level cleanup (existing behavior)

### Optional: client_id in env.apply

For clarity, `server.session.env.apply` can include `client_id` field, but it's not required—agent can infer from connection context.

**Cleanup methods:**
```rust
// NEW: per-client cleanup (on detach)
pub async fn cleanup_client_scripts(&self, client_id: &str) {
    // Scan /tmp/, delete all nession-{source,unsource}-{client_id}-* files
}

// EXISTING: per-session cleanup (on session kill)
pub async fn cleanup_session_scripts(&self, session_name: &str) {
    // Scan /tmp/, delete all nession-{source,unsource}-*-{session_name}-* files
}
```

### WebSocket Handler Changes

**Connection tracking:**
```rust
// Maintain mapping: connection_id → client_id
sessions: Arc<Mutex<HashMap<ConnectionId, ClientId>>>
```

**Auth handling:**
- Extract `client_id` from `ClientAuth` message
- If not provided, generate UUID
- Store in connection mapping
- Return in `AuthResponse`

**Detach handling:**
- On `CLIENT_DETACH` or WebSocket close:
  - Retrieve `client_id` from connection mapping
  - Call `cleanup_client_scripts(client_id)`
  - Remove from mapping

**source_env/unsource_env calls:**
- Retrieve `client_id` from current connection context
- Pass to `tmux.source_env(client_id, ...)`

### Call Sites Updated

- `server_client.rs:673` — `source_env` in `server.session.env.apply` handler
- `server_client.rs:705` — `unsource_env` in `server.session.env.unset` handler
- WebSocket detach handlers — call `cleanup_client_scripts`

## Server-Side Changes

### Auth Handling

- Receive `client_id` from client auth message
- Maintain `connection_id → client_id` mapping in memory
- Optional: forward `client_id` in `env.apply` messages to agent (for clarity)

### Session Kill

- Existing logic unchanged
- `kill_session` calls `cleanup_session_scripts(session_name)` (cleans all clients)

### Backward Compatibility

- Old client → server generates client_id, returns in response
- Old agent → ignores client_id, uses session-level cleanup

## Client-Side Changes

### Web UI (web/src/services/websocket.ts)

```typescript
// On first connection:
const clientId = localStorage.getItem('nession_client_id') || crypto.randomUUID();
localStorage.setItem('nession_client_id', clientId);

// On every connection:
wsService.connect(token, clientId);
```

### CLI (crates/nession-cli/src/client/)

```rust
// On first run:
let client_id = read_client_id().unwrap_or_else(|| {
    let id = Uuid::new_v4().to_string();
    write_client_id(&id);
    id
});

// On every connection:
client.connect(token, client_id);
```

### Edge Cases

**Client clears browser storage:**
- New client_id generated → treated as new client
- Previous env scripts become "orphans" (not cleaned via normal detach)
- Mitigation: session kill cleans all scripts; or periodic orphan cleanup (future optimization)

## Migration Strategy

### Deployment Order

1. Deploy new agent (backward compatible with old clients)
2. Deploy new client (enjoys per-client isolation)
3. No simultaneous upgrade required

### Existing /tmp/ Scripts

Old-format scripts (`/tmp/nession-source-{session}-{env}`) won't be auto-cleaned after deployment.

**Options:**
- Manual one-time cleanup
- Agent startup scan to remove old-format scripts (optional)

## Testing Strategy

### Unit Tests

1. **TmuxManager:**
   - `source_env` generates correct script path with client_id
   - `cleanup_client_scripts` deletes only specified client's scripts
   - `cleanup_session_scripts` deletes all scripts for session (all clients)

2. **Protocol:**
   - client_id field serialization/deserialization
   - Backward compatibility: missing client_id doesn't error

3. **Agent WebSocket:**
   - Auth message handles client_id
   - Detach calls `cleanup_client_scripts`
   - Multi-client: A detach doesn't affect B's scripts

### Integration Tests

1. **Multi-client scenario:**
   - Client A attaches session X, sources "staging.env"
   - Client B attaches session X, sources "prod.env"
   - Client A detaches → verify A's scripts cleaned, B's preserved
   - Session kill → verify all scripts cleaned

2. **Reconnect scenario:**
   - Client A attaches, sources env, detaches
   - Client A reconnects (same client_id), attaches → verify can access previous env tracking
   - Client A detaches → verify scripts cleaned

### Manual Testing (Playwright)

- Two browser windows (different client_ids) attach to same session
- Verify EnvPanel shows correct sourced envs per client
- Close one window → verify other's envs unaffected

## Behavior Changes

- Multiple clients attaching to same session: each client's envs tracked independently
- Client detaches: only that client's env scripts cleaned up
- Session killed: all clients' env scripts cleaned up (existing behavior)
- Backward compatible: old clients/agents continue to work with degraded (session-level) behavior
