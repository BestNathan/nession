# Nession 1.x — Session & Workspace

**Product generation:** In development; this document defines the target experience, not shipped functionality  
**Positioning:** A continuous work environment organized around Sessions and Workspaces

## Product proposition

0.x helps users **control a remote terminal**. 1.x aims to help users **continue their work** without reconstructing its context whenever they switch devices, Sessions, environments, or tools.

The user should think first about the work in progress, not which Agent to visit or which independent tool to launch. Nession makes **Session** the primary active work object and **Workspace** the coherent context around that work. Capabilities contribute useful state and actions within that context.

> **1.x promise:** Return to a Session, understand the work around it, and use relevant capabilities in one continuous Workspace experience.

## Primary user journeys

### Return to the current work

A user opens Nession, finds the Session associated with their work, and resumes interaction. They should not need to navigate an Agent hierarchy before getting back to the work. The product distinguishes Session lifecycle, client attachment, and infrastructure connectivity so that a temporary disconnection is not mistaken for lost work.

### Deepen from Session into Workspace

A Session is the primary active work entry. Its Terminal remains an important live surface for shells, TUIs, coding agents, and operational workloads. When the user needs more context, they can open the associated Workspace to inspect resources, state, history, and actions **without losing which Session and resource brought them there**.

### Use capabilities as part of work

Files, Git, agent integrations, environment controls, and other capabilities become useful in the Session or Workspace context. Their presence and disclosure follow the work, not a permanent feature directory. Nession owns the common experience; integrations contribute semantic capability and actions.

### Move across devices and environments

Working context survives changes of client attachment. Workspace represents logical work; a Workspace Location describes where a portion of that work exists or executes. Agent, provider, directory, and transport are visible when relevant, not mandatory parents of the user's navigation. Full multi-location behavior can mature incrementally rather than being implied as already shipped.

## Core product model

| Concept | Role in 1.x |
| --- | --- |
| **Session** | Primary active work object; the entry point for returning to ongoing work. |
| **Workspace** | Logical context for the work, its resources, locations, and deeper capabilities; not a generic feature lobby. |
| **Workspace Location** | Physical or provider-backed place where part of the work lives or runs. |
| **Terminal** | Default live interaction surface for terminal workloads; not the definition of all possible work. |
| **Capability** | Contextual extension of what users can see or do, with consistent state, actions, and presentation. |
| **Agent** | Execution/connectivity infrastructure; useful context but not the default navigation hierarchy. |

Precise semantics, state dimensions, IA, and disclosure depth remain owned by [the current product model](../design/product-model.md), [Workspace model](../design/workspace.md), and [capability disclosure contract](../design/capability-emergence.md). This document owns the **generation-level user promise**, not competing API or UI specifications.

## Intended product scope

The 1.x generation focuses on these outcomes:

1. **Session continuity:** Sessions are easy to discover, manage, revisit, and interact with reliably across attachment changes.
2. **Work-centric organization:** navigation and context begin with Session and Workspace, rather than a remote-node feature tree.
3. **Workspace as a real work context:** resources, locations, and relevant state have coherent relationships around the work, with a path toward explicit logical Workspace identity.
4. **Unified capability experience:** built-in and extended capabilities can expose relevant state, actions, and rich views while preserving Session/Workspace context.
5. **Progressive interaction:** the active work remains central; infrastructure and advanced capability detail appear when needed rather than crowding the default surface.

Natural-language or AI-assisted interaction can be an important way to reach or operate these capabilities. It must not require every Session or workload to masquerade as a chat conversation. A shell, editor, TUI, and coding agent remain valid Session workloads.

## Boundaries and non-goals

1.x does **not**, by its positioning alone, promise:

- a fully autonomous multi-agent operating system or generalized workflow orchestrator;
- the completion of every possible capability integration;
- that one Workspace must equal one Agent, machine, terminal, or directory;
- that a product-wide conversation schema is required for ordinary Session I/O;
- a permanently visible menu entry for every registered capability;
- that every future cloud sandbox, multi-location, or AI automation feature is required for the first 1.x release.

Such changes can be scoped as concrete Requirements or considered for later product generations. Avoid converting exploratory directions into implicit 1.x release gates.

## What makes 1.x meaningfully different

The transition is a **change of product perspective**, not just more remote-control features:

| 0.x: Remote Control | 1.x: Session & Workspace |
| --- | --- |
| Find a node and operate its terminal | Find the work and return to its Session |
| Connection and terminal are the main experience | Continuity and work context are the main experience |
| Agent/topology commonly organizes access | Session/Workspace organizes the experience |
| External tools are separate destinations | Capabilities appear in relevant work context |
| Reaching execution is the main goal | Continuing work with its context is the main goal |

## Product readiness

The generation is ready to be considered a coherent 1.x product when representative users can reliably return to an existing Session, continue terminal work, open meaningful Workspace context, move into a relevant capability and back **without losing work identity or context**, and understand interruptions without confusing connectivity with Session termination.

This statement does not replace individual Issue success criteria, regression evidence, or release gates. Those prove the specific behaviors that implement this target.
