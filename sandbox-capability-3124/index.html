Functional design & verification

Agent、Session、tmux Pane、Policy、执行结果都为合成 Mock 数据；构建配置、预检与 Enter 操作绝不调用真实主机或修改实际进程。

关键路径 · 可完整点击

  1. 默认 Native：Terminal → Workspace → Sandbox，编辑 Filesystem / Network / Process；Resource / Syscall 的 KV 候选字段由模拟 Agent 发现列表提供。
  2. 点击「校验配置」运行 Mock Schema 与当前 Agent 能力预检；修改策略会清除之前的预检通过状态。
  3. 点击「Enter Sandbox」进入确认页，明确原 Native Pane 保留、启动隔离 Pane 的范围；确认后模拟启动与验证，再切换当前 Pane。
  4. 进入后显示 Inside Sandbox 及已生效配置（不是草稿），可查看执行详情或「返回 Native Pane」；原 Sandbox Pane 仍保留。
  5. 切换「仅 Memory/PIDs 委派」测试 Agent 返回的候选 Key 不包含 cpu.max；测试预检失败、启动失败、macOS、不支持和 Agent 离线，失败保留 Native/草稿。
  6. Web ↔ App，检查 App 一个 Back、Capsule 永远在其底部、配置表单独立纵向滚动。

核心对象和状态

宿主能支持 Sandbox ≠ 当前 Pane 位于 Sandbox。状态由 Agent 对 active Pane + Session instance + execution id 的观测决定，外部启动的非托管 Sandbox 不能推测为 Nession 已验证。

Policy Draft 在提交前可编辑；Effective Policy 是成功执行后、Agent 验证并持续可查询的只读配置。预检与 Enter 是两个不同动作。

运行时设计约束

现有 #2681 仅在创建 Session 时提供启动屏障。新的 Enter 需要 Agent 创建 同一个逻辑 Session 的隔离 Pane，验证 Linux Bubblewrap / macOS Seatbelt 后切换焦点。原 Native Pane 保留，失败时不影响原 shell，不向已有 Pane 注入文本。

Return to Native 只是切换焦点，不代表 Sandbox 的进程已经终止。完整的结束/清理与重连需在后端代码及独立 Case 中实现、验收。

信息架构和证据边界

Web：WebLayout → Sidebar + ShellMain → WorkspacePanel → WorkspaceShell → Sandbox 能力本地视图。App：AppLayers → WorkspacePanel 唯一 AppPageHeader/Back → WorkspaceShell → Sandbox 配置/确认/详情。没有新的永久 Sandbox 页面。

字体、终端渲染和样式为 Nession token 快照基础上的近似，非真实 React / xterm 画面。静态校验与合成 DOM 测试不等于 Chromium 或真实原生隔离验证。
