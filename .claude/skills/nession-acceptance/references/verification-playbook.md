# SC verification playbook — choose proof before choosing an executor

This is the **task procedure** for Nession Requirement authors, Developer/Reviewer Agents and Acceptance operators. **Select a primary scene in [the eight-scenario catalog](scenario-catalog.md) before choosing any proof method; the catalog's hard-stop rule applies when no valid or feasible proof exists.** The executable contracts remain `scripts/acceptance-plan.mjs`, `scripts/requirement-acceptance.mjs`, the trusted workflows, and the source-aligned Case contract in `docs/architecture/acceptance-cases.md`. Do not encode a second acceptance schema, verifier registry or result policy here.

## Two supported proof methods, several proof families

- `method: agent`: read-only evaluation of **existing, concrete** source, deterministic Gate/test output, CI receipts and authenticated external records. The Agent may run **safe local narrow preflight** while developing, but its opinion or a command it did not execute/observe is not proof of a runtime scenario. It cannot grant itself privileged credentials or issue-write authority.
- `method: case`: an **executed source-aligned Case** with observable assertions and trusted result ingestion. The Case runner owns runtime setup, verifier steps, reporting and cleanup. Select a verifier by the behavior under test, not by whether it is convenient to launch a browser.
- Human review, exploratory testing, prototypes and screenshots are **supporting evidence**, not a third supported `method`. If they cannot be transformed into a trustworthy, reproducible Case/attestation, the SC remains `Pending` until its verification contract and execution path exist. All Web/App browser interaction and visual acceptance is standardized on **Chromium + Playwright**; physical phones, Mobile Safari and installed iOS Apps are not required acceptance executors.

Do not introduce `method: manual`, `browser`, `unit` or `remote` in Issue YAML: `scripts/acceptance-plan.mjs` accepts only `agent | case`. Browser/protocol/runtime are **Case verifier types**, not SC methods; local/staging/deployed are **execution contexts**, not methods.

## Scenario-specific playbooks

The [SC scenario catalog](scenario-catalog.md) provides the eight mandatory classifications and stop/clarification rules. The procedures below define **proof**, not implementation. Use only the relevant section; the native OS and GitHub security profiles below supply additional detail for SCN-03 and SCN-05.

### SCN-01: Static and deterministic contract

**Trigger:** the outcome is a schema/API/parser/policy/instruction invariant that is fully decidable from exact-source artifacts and deterministic tests. **Components:** repository checkout, `./gates/run --describe <id>`, focused Gate/self-test, source diff and negative fixtures. **Procedure:** identify the owner and expected positive/negative input; run or obtain an independent exact-SHA check; inspect that it rejects the original violation; confirm no runtime claim is hidden in the wording. **Pass:** named code path + concrete assertion/result + exact SHA. **Pending/stop:** no independent test/source evidence or the claim actually requires kernel, provider, browser, GitHub server or deployed behavior—reclassify or split rather than accept source opinion.

### SCN-02: Chromium browser and App

**Trigger:** actual Web/App interaction, visual layout, touch, focus, clipboard, scroll, accessibility or xterm rendering. **Components:** canonical Chromium + Playwright `browser` Case, viewports from `design/contracts/viewports.json`, representative state/gesture fixtures, screenshots/traces for diagnosis. **Procedure:** create deterministic initial state, act with real browser input/emulated touch, assert DOM/computed style/accessibility/xterm-visible state and no relevant regression; compare visual baseline only with justified approved changes. **Pass:** reproducible action→observed result, viewport/input context, exact-SHA Case assertion and trusted receipt. **Pending/stop:** no browser Case or assertion; prototype HTML, an isolated unit test or Safari/native phone observation is not substitute production UI proof. OS-only Safari gesture/IME behavior is outside this contract; model *Nession-owned* visualViewport/safe-area state deterministically without claiming native OS coverage.

### SCN-03: Terminal, protocol and runtime

**Trigger:** Session, Agent/Server, tmux, transport, process, reconnect, ordered output, isolation or launch-lifecycle behavior. **Components:** canonical isolated `full-stack-local` CI runtime when supported, source-aligned `protocol` and/or `runtime` verifiers, optionally Chromium when rendering is part of the SC. **Procedure:** establish isolated tmux socket/home and exact session/transport generation; run an observable normal path and a bounded fault/negative path; assert ordered event/byte/state transitions, cleanup, no duplicate output and ownership boundaries. **Pass:** raw decisive protocol/process assertions and isolation/teardown evidence bound to exact SHA and Case Run. **Pending/stop:** an uncontrolled local tmux, a source-only implementation assertion, or missing safe CI runtime does not prove the behavior. For *native enforcement* run the [OS privilege profile](#os-native-privileges-kernel-enforcement-and-sandbox-acceptance) rather than assuming normal `full-stack-local` grants cgroups/seccomp.

### SCN-04: Agent, provider and Store integration

**Trigger:** real provider, credential scope, Agent dispatch/handoff, Store CAS, multi-Run/recovery, authenticated readback. **Components:** existing trusted main-owned isolated staging/execution lane, controlled credentials and Store namespace, precise Workflow/Run and artifact/Store readers. **Procedure:** bind source+consumer identity and exact SHA; execute or inspect an independently attested real positive path and negative replay/incorrect identity/error; verify state before/after and immutable receipt; avoid broad provider calls when a narrow existing receipt proves the stated assertion. **Pass:** independent authenticated provider/Store/Run evidence, no invented responses. **Pending/stop:** only fake provider, unavailable approved credentials, untrusted PR-head write access or an inferred external service outcome. Do not move the SC to main merely to sidestep missing staging evidence.

### SCN-05: CI and trusted workflows

**Trigger:** workflow event/branch timing, trigger deduplication, Gate verdict, source provenance, scoped authority, Result ingestion, GitHub policy. **Components:** workflow source/contract Gate, GitHub REST read-only Run/Attempt/job/step observations and source artifact SHA, deterministic negative event fixtures; only when needed, an authorized main-owned live dispatch. **Procedure:** define allowed and forbidden event/source identity; prove the authorized path selects precisely the expected job/criterion and forbidden/stale/forged path cannot publish or mutate; correlate both workflows' exact IDs/attempts and source revision. **Pass:** authenticated GitHub evidence or executable deterministic source assertion appropriate to the wording, with actual negative result. **Pending/stop:** a YAML trigger or generic CI green cannot prove GitHub's privileged routing. For **server-side Ruleset, App writer or Environment authorization**, run the [GitHub security profile](#github-security-policy-and-trusted-writer-acceptance) with safe canary evidence; do not expose writer keys to Acceptance.

### SCN-06: Performance, resources and compatibility

**Trigger:** latency, disk/network work, cache reuse, memory/CPU efficiency, throughput/bounds, concurrency, native-platform compatibility. **Components:** pinned workload/data/toolchain, explicit baseline and candidate, matching runner class/kernel/OS where meaningful, measured counters/traces, reproducible script/Gate and/or source-aligned Case. **Procedure:** state unit, budget/regression threshold, warm/cold or load conditions, sample count and confidence/variance rule *before* reading results; measure comparable runs; verify correctness/failure-path invariants were not weakened while reducing time or resources. For true macOS APFS or other native feature, require a valid native readback, not Linux/mock inference. **Pass:** bounded measurements and exact runner/source identity showing both behavior and measurable criterion. **Pending/stop:** missing baseline, incomparable machines/inputs, no controlled samples, invented “faster” assertion. Use SCN-03/native-os instead if a hard kernel security limit, rather than average performance, is the SC.

### SCN-07: Deployed and remote environment

**Trigger:** observed staging/production workload identity, GitOps reconciliation, actual VPN/network/service policy, deployed revision or protected-environment safety. **Components:** authenticated `Deploy / Identity` record, exact image digests and GitOps revision, separately authorized remote read-only route/probe; explicit `Acceptance / Cases` deployed run when implemented. **Procedure:** prove source SHA→image digests→environment→workload UID/revision; verify intended remote positive/negative behavior through real approved network route without mutating unrelated workloads. **Pass:** exact environment binding, authenticated deployment record + actual remote assertion and receipt. **Pending/stop:** main merge, local stack, image build or pretend VPN cannot prove deployment. The currently specified `remote-staging`/`remote-production` profiles are not generally available; do not promise or silently substitute a future lane. Existing #1616 deployed+agent mismatch needs owner review.

### SCN-08: Documents, Knowledge and prototype artifacts

**Trigger:** actual authored/published document, generated index, link behavior, Knowledge append-only ledger, prototype source/manifest/HTML gallery. **Components:** exact file tree/content/frontmatter/schema/link validator, immutable publication commit, trusted readback of Knowledge/Pages/HTTP where claimed; browser inspection of an interactive prototype in Chromium is **artifact proof only**, not production UI acceptance. **Procedure:** verify required files/sections/contents; inspect generated references and published artifact revision/readability, and the appropriate safety/read-only rules of the publisher; keep a clear mock-vs-live label. **Pass:** exact content + source SHA + independent publication/readback if required. **Pending/stop:** an unpublished URL, unverified source or mock-only interaction cannot prove delivery or real product behavior. For **actual GitHub writer authorization** of the Knowledge branch, classify that distinct assertion as SCN-05/github-security rather than passing it from ledger formatting checks.

## OS-native privileges, kernel enforcement and sandbox acceptance

Use this family only when a Success Criterion promises **effective OS isolation, policy enforcement, resource quotas or native host behavior**, not for ordinary Rust/source/portable unit tests. See [#2681](https://github.com/BestNathan/nession/issues/2681) for the Nession SandboxPolicy/Backend owner and [#2514](https://github.com/BestNathan/nession/issues/2514) for **read-only** process-discovery/fallback semantics. Do not turn the Playbook into a competing Sandbox policy specification or introduce a universal privileged CI gate.

1. **Separate the actual guarantee by platform and execution scope.** Name the policy key and its native enforcement owner: e.g. Linux `process.linux_namespaces`, `resource.cgroup_v2`, `syscall.seccomp`, `filesystem.access`, `network`, or a separately verified macOS Seatbelt backend. State whether the promise covers one on-demand `SandboxExecution` and its descendants or a different proven scope; Nession's shared tmux server, Agent and Native Sessions must not accidentally inherit it. Never map macOS `setrlimit` to cgroup v2 or claim macOS namespaces/seccomp.
2. **Probe the actual Runner capabilities before selecting it.** Record OS/kernel version and architecture; namespace creation permitted under the Runner's own userns/security/LSM/container constraints; working bubblewrap/helper where required; actual readable **and delegated writable** cgroup v2 controllers under its parent; seccomp/filter/no_new_privs support; network/proxy policy facilities; or genuine Seatbelt availability on macOS. Do not infer functionality from a file's existence, `uname`, an installed executable or successful mock. Prefer an approved narrowly scoped Linux/macOS runner or operator-managed isolated test host; **do not grant root, `--privileged`, host PID/network, host Docker socket or broad host mounts to normal PR/Agent code** just to pass.
3. **Start a bounded disposable execution and compare against a control.** The trusted Case launcher owns an isolated tmp/root/workspace, process tree, per-execution kernel resources and test-only network destinations. Assert policy is installed **before user code runs**. Verify intended permitted behavior (shell/TUI, normal filesystem operations, permitted network, fork/exec, resize/signals as relevant) and forbidden behavior (unlisted host paths/FDs/sockets, other namespace processes, denied IP/domain/port, prohibited syscall, quota crossing) using controlled fixtures. A test failure to *set up* the isolation is not evidence that the isolation denied an operation.
4. **Prove each native mechanism with observable kernel facts and negative probes.** Linux namespace identity/mount view and PID/IPC/user boundary must be examined **from inside and outside** the execution. For `resource.cgroup_v2`, read effective controller values, compare `/proc/<pid>/cgroup`/actual membership for the initial process and descendants, verify shared Agent/tmux exclusion, and use bounded limit probes plus appropriate `memory.events`, `pids.events` or `cpu.stat` observations. For `syscall.seccomp`, inspect actual filter/no_new_privs state and a harmless known-blocked syscall result, with allowed shell/tool operations still working; seccomp filters apply to descendants as proven, not by source review. For network policy, exercise both allowed and forbidden DNS/IP/port destinations, host-local/private/metadata and direct/proxy-bypass paths against **test fixtures**; a client proxy environment variable alone is not enforcement. For macOS, verify actual Seatbelt behavior with safe allow/deny fixtures; Linux-native keys must return explicit `UnsupportedPolicy`, not silently downgrade.
5. **Prove lifecycle and fail-closed behavior.** Test missing delegated controller, unavailable namespace/backend, failed setup/partial launch, permission denial and timeout. Required policy must refuse launch without silently falling back to Native; do not kill or alter unrelated host/shared tmux/Agent processes. For a running execution, verify child inheritance, tmux attach/detach/reconnect, exit, interruption, owned resource cleanup and Agent-restart reconciliation **only when claimed by the SC**. Keep memory/process/CPU/network probes bounded and independently cancelable; never perform host-wide destructive pressure tests or arbitrary escape attempts.
6. **Select executable timing and independent evidence.** Isolated deterministic policy validation can run at `when: pr` with `method: case` when the exact approved runner supports it. Actual Server+Agent+tmux/kernel behavior may require `merged/staging` if that is the earliest **available, authorized** trusted integration lane, not merely because the word “sandbox” appears. Use the existing source-aligned `type: runtime` Case and optional `type: protocol` or Chromium+Playwright `type: browser` verifiers for user-visible behavior. Keep Linux/macOS observations distinct: neither a container mock nor another OS is proof for the requested platform. If no capable approved runner or authenticated native observation exists, the criterion is `Pending` with an explicit prerequisite; observed failure to enforce an asserted policy on a capable target is `Fail`; an expected denial is a positive assertion, not product failure.

**Minimum proof receipt:** target commit/Issue/SC/contract digest; Runner identity and kernel/OS/architecture; which native capability probes passed or were unavailable; execution ID, requested policy and effective kernel-state observations (namespace, cgroup controller/membership, filter state, network/FS or Seatbelt decision as applicable); specific allowed/denied input and actual outcome; parent/child and shared-process boundaries; bounded teardown and leak check; workflow Run ID/Attempt and authenticated artifact/checksum. Redact process environment, credentials, user paths and raw terminal contents. A green Gate, bubblewrap command exit code or root-like UID inside a user namespace is **not** proof of effective isolation.

**Runner trust boundary:** The normal Agent and standard untrusted PR code do **not** gain new privileges. If a platform-specific helper needs elevated host permissions, an explicitly authorized, minimized **trusted test harness** must own that setup and isolate untrusted target execution; a read-only verifier can consume its authenticated receipt. The installed Case runner currently provides a `full-stack-local` runtime in approved CI; this Playbook **does not claim** that it already supplies delegated cgroup controllers, host seccomp test capabilities, network policy enforcement or a native macOS runner. Establish and verify any missing lane before calling SC Pass.

## GitHub security policy and trusted-writer acceptance

Use this procedure **only for SCs that actually require GitHub-side authorization/enforcement** (Rulesets, branch protection, App permissions, protected Actions Environments or privileged workflow routing). Ordinary source-only workflow/config refactors should use the static or main-identity proof families above rather than requiring an expensive privileged canary.

1. **Define the policy invariant and affected authority.** Name the exact protected repo/ref or Workflow, operations permitted/denied, intended GitHub App/actor type, and the policy owner. Identify whether the SC asserts only configured policy, actual **server-enforced** authorization, or secret/dispatch isolation. Do not conflate writer-side CAS/validator/Gates with GitHub's authorization decision.
2. **Read effective live settings without modifying them.** With a read-only authorized GitHub REST client, resolve the target ref's actual branch protection/applicable Rulesets, enforcement status, conditions, rule types and bypass actors, installed App identity/permissions, and relevant Environment branch/reviewer restrictions. Read specific rulesets if the aggregate endpoint omits bypass details. If API permissions hide an essential field, do not infer a safe empty value: record `Pending` and the missing administration/readback capability.
3. **Prove allow and deny only on a disposable protected canary.** If the SC asserts real enforcement, configure equivalent isolated rules on a unique test ref or test repository **under separately authorized administration**, never on a live Store/Knowledge/main ref. First demonstrate the unauthorized principal can write an **unprotected control ref**: otherwise a 401/403 cannot be attributed to Ruleset enforcement. Then require an actual GitHub denial for its protected normal update (e.g. matching ruleset rejection / Rule Suite record), plus an unchanged canary head. With the **designated App installation identity**, prove the permitted fast-forward/CAS write succeeds and its commit is read back. For append-only policies, prove the **same App** cannot non-fast-forward, delete or bypass a zero-bypass rule, again preserving the ref. Test only the forbidden operations relevant to the SC; stop and flag `Fail` if an unintended write succeeds. Clean up only owned canary resources under approved control.
4. **Verify privileged routing and source trust separately.** Inspect main-owned workflow source, event/ref/actor admission, `pull_request_target` and checkout constraints, token mint timing and minimal permission scopes, Environment approvals/branch restrictions, and denial of arbitrary PR-head/model/issue-comment credential access. Where behavior is part of the SC, obtain authentic source/consumer GitHub Run/Attempt receipts and bounded negative routing tests; a YAML `permissions:` declaration alone cannot prove secrets were unavailable to all other execution paths.
5. **Separate probe authority from Acceptance.** Write probes run only in an explicit **trusted main-owned operator/probe job** with scoped temporary credentials and review/approval; no untrusted PR code, model Agent, standard source-aligned Acceptance Case or GitHub Issue updater gets Ruleset-admin/writer secrets. The Case, when needed, is **read-only** and independently validates authenticated probe artifacts, policy/actor/ref identities and immutable GitHub evidence through the existing trusted ingester.
6. **Recheck the real target and decide per SC.** A canary proves GitHub's enforcement for equivalent test rules, **not** that real target protection was activated. Read back the effective Rulesets on the actual ref after activation and verify exact scope and bypass lists. For real enforcement, `Pass` requires *both* live readback and real allow/deny receipts relevant to that SC, tied to the expected actor, Run/Attempt, head-before/after SHA and policy IDs. For configuration-only SCs, readback plus independent auth/config evidence can suffice. Missing App, required permission, canary, ruleset readback, protected job or genuine denial => `Pending`; a demonstrable policy bypass => `Fail`. Do not substitute fixtures, a green CI job, source comments or a manual screenshot for GitHub authorization.

**Evidence handoff:** record expected rule → tested identity/operation → GitHub response (HTTP status / ruleset violation or Rule Suite) → before/after ref SHA → independent verdict. Include repository, target + canary refs, applied Ruleset IDs/active conditions/bypass principals, App ID (**never token/key**), source/consumer workflow path, event/ref/SHA, Run ID/Attempt, credential boundary, time and artifact checksum. Minimize/redact any private repo contents or credential-bearing logs.

**Existing owners and examples:** `docs/engineering/knowledge-writer-protection.md` and [#2358](https://github.com/BestNathan/nession/issues/2358) define the dedicated Knowledge App, layered writer-identity/zero-bypass append-only Rulesets, control ref and canary operations. Do **not** create an independent Ruleset schema or a generic privileged probe framework in this Playbook. [#1690](https://github.com/BestNathan/nession/issues/1690) explicitly defers stronger cross-writer administrative protection for Run Stores in the current trust scope; referencing this family does not reactivate that deferred work or make it a universal gate.

**Mismatch to flag, not silently rewrite:** #1616 currently declares `when: deployed` + `method: agent` for SC-03–07, but the implemented explicit deployed path is `Acceptance / Cases` and the Agent eligibility path excludes deployed proof. Review each existing SC's wording and historical evidence, propose an explicit contract migration, and hold it `Pending` until an authenticated, executable route exists. Changing a live Plan changes its digest; use an Issue discussion and preserve old receipts.

## Which environment may execute?

| Environment / authority | Allowed work | Not sufficient for |
|---|---|---|
| Developer Agent's **isolated worktree** | Source review, `./gates/run --list/--describe/--validate`, narrow safe Gates/unit tests, `./e2e/run --list`, `./e2e/run --validate`, controlled dev-browser exploration | Formal full-stack E2E, privileged provider/Store/production access, automatic trusted Issue update |
| Approved **CI full-stack-local** | Exact-SHA `./e2e/run acceptance` using `e2e/acceptance/cases/<issue>/<SC>/`; Chromium+Playwright Browser/Protocol/Runtime verifiers; isolated Server/Agent/tmux lifecycle and artifact capture | Real remote deployment identity or privileged production access; unverified delegated cgroup/namespace/seccomp/Seatbelt capability; Web/App platform-specific OS behavior outside the Chromium verification contract |
| Trusted **merged staging integration** | Isolated real-provider/Store/security integration using protected credentials and exact staging SHA, when the approved lane exists | Main-only identity and production state; nonexistent staging lane cannot be substituted with a main canary |
| Authenticated **main-only lane** | Minimal main-specific workflow identity/dispatch observation | Generic cross-component behavior that could be proven in PR/staging; deployment evidence |
| Explicit **deployed / remote** lane | Read-only environment observation only with approved identity, network and safe probe model; not a Web/App mobile-device lane | Local simulation, unverified release tag, mock, or screenshot without trusted provenance |

**Unified Web/App proof boundary:** Use Chromium + Playwright for all Web/App interaction and visual SCs on both desktop and mobile layouts. Mobile coverage uses pinned viewport dimensions, mobile/touch context, touch and pointer cancellation, horizontal/vertical gestures, landscape, focus/IME-related application states, scroll ownership and visual baselines. When an OS feature cannot be faithfully emulated (such as iOS Safari's native edge navigation, system keyboard or safe-area behavior), constrain the assertion to Nession-owned behavior and model relevant visualViewport/safe-area inputs with deterministic test fixtures where necessary. Document emulator limitations honestly; never require physical Safari/iOS evidence as a separate gate or mark an otherwise proven app-level SC `Pending` solely for lack of a phone. This does **not** claim Chromium proves actual Safari OS behavior.

Repository policy: **do not run the full E2E suite or full-stack Acceptance Case on a developer machine**; see `e2e/README.md`. Do not use `npx playwright test`, `CI=true` or direct runtime invocation to bypass it. Cases are run through the canonical CI/Actions interface, not by the model with production secrets. The source-aligned local runner is currently `full-stack-local` **in authorized CI**; `remote-staging` and `remote-production` execution profiles are specified but not generally enabled. An authenticated deployment identity path alone does not prove remote behavior.

## Per-SC execution procedure

1. **State the predicate.** Write one observable outcome and at least one concrete assertion (include a negative/failure case when it is part of the promise). Split an SC if code-policy proof and real-integrated behavior need different timing/methods. Avoid acceptance criteria that merely describe implementation.
2. **Inventory prerequisites.** Which exact source SHA, OS/kernel/architecture, effective namespace/cgroup delegation/seccomp/Seatbelt capabilities, Chromium viewport/input emulation, tmux/network, provider credentials, Store namespace, GitHub permissions or deployed identity must exist? Identify which runner or tool can actually access them. Check the current `e2e/run` inventory and Case support rather than assuming every Agent sandbox has a browser, Docker, privileged Linux, VPN or model API.
3. **Choose earliest safe `when` and executable `method`.** Prefer `pr` where equivalent reliable evidence exists; only use merged staging/main/deployed for properties that need those boundaries. If the proof is runtime behavior, require a Case and its source-aligned manifest; if an existing read-only authenticated receipt truly proves it, Agent may assess that receipt.
4. **Preflight locally, safely.** Run available narrow Gates/tests, inspect failures, use controlled dev-browser checks where relevant; record unresolved prerequisites. This helps implementation but **does not** automatically project a formal SC Pass.
5. **Run the authoritative proof.** For Agent proof use `Agent / SC Acceptance` and its exact target context. For Case proof create `e2e/acceptance/cases/<issue>/<SC>/case.yaml` and verifier(s), run `Acceptance / Cases`/`Acceptance / Case Smoke` as eligible through trusted CI and `./e2e/run acceptance`. Let the owning runner set up and tear down the runtime; the Case manifest must match the Issue stage.
6. **Evaluate and freeze evidence.** Verify target SHA, Issue/SC contract digest, Case revision/tree SHA (for Cases), workflow Run ID/Attempt, method, stage/environment, real assertion results, and immutable artifact/record links. The trusted ingester/projector alone updates `Acceptance Report` and the SC checkbox. Developer/Case/model code must not edit them.
7. **Handle missing capability explicitly.** Missing runner, credentials, VPN, Chromium/Playwright setup, Case, artifact or observable assertion = `Pending` with a named prerequisite/owner and next proof step. Observed product assertion false = `Fail`; infrastructure inability to execute is not automatically product Fail. `N/A` requires a legitimate non-applicability reason, not “cannot run locally”. Do not move the stage to main or broaden to Full E2E just to make a workflow green.

## Evidence checklist / handoff

For every SC, write down: **expected → action/input → actual observation → verdict**; the exact target SHA and source/Issue/SC digest; the specific Gate/test/Case verifier and decisive assertion; approved execution environment/profile; workflow Run/Attempt and artifact or code-path references; negative/failure/cleanup observations where relevant; and any evidence gap. Redact secrets, tokens, private routes and user terminal content.

A screenshot or Playwright trace backs a UI assertion but is not the sole trust anchor. A passing workflow, CI check or model-generated summary is not itself SC Pass. A prototype is design review, not production proof. An old SHA or mismatched deployment cannot establish current-SHA acceptance.
