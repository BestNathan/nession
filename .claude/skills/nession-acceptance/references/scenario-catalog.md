# SC verification scenario catalog — classify before writing Acceptance Plan

This task-local catalog is **mandatory for new/rewritten Nession Issue Success Criteria**. It selects a **proof scenario**, not a new Acceptance Plan field, Case verifier type, `verification:*` tier, E2E obligation, domain model, or alternate rule owner. Read [verification-playbook.md](verification-playbook.md) for the corresponding execution procedure, components, evidence, and restrictions. Executable truth stays in `scripts/acceptance-plan.mjs`, `docs/architecture/acceptance-cases.md`, the Gate owners and trusted workflows.

## Eight primary scenarios

Choose **one primary scenario per SC** based on the **observable predicate**. Multiple verification techniques may support it; use the listed specialized profile when relevant. One Issue may span many scenarios. Examples are real Nession issues and identify the kind of proof, not a claim that their current SCs have passed.

**Scenario is not stage or verification tier.** Select the earliest safe `when: pr | merged | deployed` and actual `method: agent | case` separately, using the live parser and existing trusted execution paths. `verification:scoped|integration|full` and Issue E2E New/Regression obligations remain independently owned by `nession-writing-requirements`. The table's default recommendations never upgrade an SC to Full E2E automatically.

## Mandatory SC authoring routing (new or materially revised Issue)

1. **Turn each requested result into an observable assertion** (initial state, action/trigger, actual outcome and crucial negative/regression checks). Reject implementation-only checks such as “write a module” unless there is an independently observable deliverable.
2. **Choose exactly one primary `SCN-01..08`**, plus a specialized profile if relevant (`SCN-03/native-os`, `SCN-05/github-security`). Record the selection in short Issue prose when it helps audit a mixed plan; do **not** add scenario keys to Acceptance Plan YAML or the trusted result schema.
3. **Read the matching section in the playbook** and identify the components/probe, controlled input, decisive assertion, safe Runner/credential requirements, evidence record and the **earliest eligible execution boundary**. A primary scenario may require multiple verifier types; do not label `agent` solely because source can be read.
4. **Test feasibility before publishing the plan.** Is there an actual supported Case/Gate/read-only authenticated receipt path, or a concrete approved trusted owner that can supply the missing native/remote/canary probe? Name the dependency. Existing `Pending` SCs remain Pending if the lane does not yet exist; a proposed *new* SC that cannot be objectively proved as written must not be finalized by guessing.
5. **Split incompatible assertions.** If one SC mixes static proof at PR with real provider/OS/production enforcement at staging/deployed, split into separately stable SC IDs with independent Plans. Do not expand one SC into a whole-system E2E obligation just to fit a category.
6. **Only then create the SCs, canonical Acceptance Plan and initial Pending Report.** E2E Selection and the optional Prototype decision are independent. Reuse existing evidence only if the current assertion/contract/SHA still match; never change historical trusted results manually.

## Hard stop: uncovered or unverifiable scenario

**STOP before creating/finalizing or materially rewriting an Issue's SC/Plan and ask the product owner** when any one of these is true:

- No `SCN-01..08` describes the actual requested **proof**, even after considering a legitimate combination or splitting into distinct SCs.
- The proposed SC is not externally observable or lacks a decisive Pass/Fail criterion; an Agent would have to infer success from intent, plausibility, design prose or its own opinion.
- The chosen scenario demands a verifier/tool/credential/host/kernel/real provider/remote profile that **cannot be named as a feasible approved path**; the only current “proof” would be a mock, forbidden local Full E2E, fabricated auth, unsafe broad privileged runner or an unrelated green Gate.
- There is no safe way to perform the required authorization/denial, pressure, OS-escape, destructive or production probe, or its authority would cross the trusted PR/Agent boundary.
- Two plausible interpretations would lead to materially different acceptance criteria or trust boundaries; do not choose one silently.

Ask **one focused question** with the blocked SC, the missing scenario/capability, and concrete choices (scope the assertion to supported evidence, explicitly authorize/provision a safe runner or probe, or defer/remove the unprovable outcome). **Do not** silently invent a ninth scenario, new `method`, `N/A`, lower the SC, move it to main, or issue a pretend Pass to continue. After owner decision, update this catalog/playbook **only if** a genuinely reusable scenario is missing, not to accommodate a one-off assertion.

**Existing Issues:** do not stop their entire execution or erase evidence just because a historic SC lacks a now-preferred scenario. Identify it as a mapping/feasibility exception, preserve its historical SC/Plan/Report, leave unproved stage results `Pending`, and request a scoped owner decision before a material contract migration.

## Review checklist

Before handoff, every SC must answer: **Which scenario? What exact assertion? Which trusted method + stage? Which real verifier and components? Which evidence source/SHA? Does the execution path actually exist?** If any required answer is missing and no safe approved path can be stated, use the hard stop above. Acceptance operators should use the same checklist again to catch drift between Issue authoring and real runner capability.
