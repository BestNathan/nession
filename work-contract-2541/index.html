Function design & verification

这是用于讨论 WorkContract 领域概念的交互设计，不是一个已实现的 Work 业务页面；产品区域不含原型开关、状态调试或假权限。

关键体验路径

  1. 从 Workspace 底部的 Work 能力进入 WorkContract 列表 → 打开详情 → Criteria，展开 SC 验证；不是新顶层 Work 页面。
  2. 切换 Thread，发送模拟评论；v1 版本和目标不应发生变化。
  3. 选择下方 Source changed，打开 Source 或 Compare；检查源内容变更不会直接覆盖发布版本。
  4. Review proposal → 确认模拟采用 v2；回到 Revision history 仍可查看 v1，执行与验收继续固定在原版本。
  5. 切换 Workspace 胶囊中的 Files / Git / Work：回到 Work 时保留已选 Contract 和 Revision。Web 独立打开 Terminal；App 内详情 Back 回 Work 列表，再 Back 回 Terminal。
  6. 切换 Access denied / Source offline / Feishu block fixture / No Work binding；检查不可用时 Work 胶囊入口消失，已打开 Work 仅作解释。切换 CSS 宽度并 Reset。

领域边界

WorkContract 是统一名词，替代 WorkItem。发布的 Definition + Criteria 不可修改；WorkThread、ExecutionRef、Verification/Evidence 是关联对象，而不是不可变定义的一部分。

Author checkbox、可信验证结果和外部 Source Revision 互不等同；SourceAdapter 的获取/授权与 ContractParser 的语义解析也必须分离。

产品视觉与尺寸

复用共享 #2758 框架。内部模拟既有 WorkspaceShell 的能力内容与底部 CapabilityCapsule：Web 的独立 Terminal 目的地与能力胶囊分离，App 的详情层级 Back 与 Workspace 胶囊并存。Work 没有自主全局导航。外部 Width/Reset/Fixtures 不进入产品屏幕。

本次按现有 WebLayout、WorkspacePanel、WorkspaceShell、AppPageHeader 的职责重建宿主与导航。Work 是 #2541 的候选 Workspace 能力，生产尚未实现；1:1 仅指 CSS 像素，仍需 Chromium 与真实 Fixture 并排验证。

证据与限制

所有合同、修订、评论、权限和 GitHub / 飞书内容是安全的内存模拟。模拟 “Adopt v2” 不向任何远端写入，不调度 Agent，不发布知识，也不产生可信 Acceptance。

静态解析、浏览器交互、Pages SHA 及生产 E2E 是四种不同证据；仅在完成各自检查后分别记录。发布后核对 prototypes/manifest.json 的 SHA。
